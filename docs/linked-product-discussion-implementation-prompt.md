## 3. 产品体验要求

### 3.1 Skill 和 Agent 详情页

在两类详情页都增加统一的「社区讨论」模块，避免两套体验：

- 主操作：`遇到问题，发求助`
- 次操作：`分享使用经验`
- 两个入口分别打开：
  - `/forum/new?contentType=question&productType=skill|agent&productId=<id>&returnTo=<当前详情路径>`
  - `/forum/new?contentType=case&productType=skill|agent&productId=<id>&returnTo=<当前详情路径>`
- 模块显示该作品最近 5 条可见关联帖子。每项至少展示：帖子类型、标题、回复数、是否已解决、发布时间。
- 空状态文案说明“还没有相关讨论”，并保留两个发帖操作。
- 增加「查看全部讨论」，进入带作品筛选的论坛列表。
- 加载失败要显示可恢复的错误状态；不能把请求失败渲染成“暂无讨论”。
- 使用共享组件或共享查询辅助函数，保持 Skill 与 Agent 行为一致。

### 3.2 带作品发帖

调整 `src/app/forum/new/page.tsx`：

- 安全解析 `contentType`、`productType`、`productId`、`returnTo`；只允许预期枚举和站内安全返回路径。
- 从详情页进入时，在表单顶部显示不可忽略的关联作品卡片，包含类型、名称和「返回作品」链接。
- 对无效、已删除或不可访问的作品参数显示明确错误，并禁止以错误关联提交；不要静默发布成无关联帖子。
- 未登录时，登录跳转必须保留完整查询参数；登录后仍要恢复关联作品、内容类型和草稿。
- 草稿需要保存 `contentType`、结构化字段和作品关联，不能只保存标题、正文、分类。
- 发帖成功后进入新帖详情，并显示「已提交审核」状态；不要直接把用户丢回原页面而看不到提交结果。
- 保留从 `/forum/new` 独立发普通帖的能力，防止现有流程回归。

内容类型在界面上调整为：

- `question` 显示为「求助」；默认分类为问题。
- `case` 显示为「经验分享」；沿用数据库中的 `case` 值，避免无必要地新增枚举。
- `discussion` 显示为「讨论」；保留给从论坛直接发帖的用户，不作为作品详情页主入口。

降低经验分享表单门槛：标题和正文继续必填；「适用场景」「执行步骤」「效果说明」作为建议填写项或轻量结构化项，其余环境、输入、输出、限制均改为可选。同步调整前端校验及 `submit_post_for_review` 的数据库校验，不能只改界面导致 RPC 仍报 `case_fields_required`。

### 3.3 关联写入与审核

继续复用 `content_product_links`，不要在 `posts` 再造一套 `product_type/product_id` 字段。

通过新的 Supabase migration 完成以下能力：

- 先执行 `supabase migration new <清晰名称>` 生成迁移文件，再编辑该文件；不要手写时间戳文件名。
- 普通已登录用户只能为自己创建的帖子建立或删除作品关联。
- `created_by` 必须等于 `auth.uid()`；客户端不能替别人写关联。
- 关联目标必须是当前可访问的 Skill 或 Agent。
- 运营角色继续拥有现有管理能力；知识条目的关联权限不能被放宽。
- 作者能读取自己尚在审核中的帖子的关联；匿名用户只能读取已发布内容的关联。
- 一篇从作品详情发出的帖子在本轮只关联一个作品；数据库现有唯一约束继续生效。

创建帖子与创建关联必须构成一个可靠操作。优先使用一个幂等、事务化的 RPC，让帖子、关联、审核提交状态一起成功或一起失败；不要留下“帖子创建成功但关联丢失”的半成品。新函数默认使用 `SECURITY INVOKER`。如果基于现有安全模型确实需要 `SECURITY DEFINER`，必须固定 `search_path`、撤销不必要执行权限、在函数内重新校验 `auth.uid()`、帖子归属、禁言状态和作品有效性，并在交付说明中解释原因。

所有 `public` 暴露表继续启用 RLS。策略要显式写 `TO authenticated` 或 `TO anon`，所有权条件使用 `(select auth.uid())`。若涉及 UPDATE，确保对应 SELECT policy、`USING` 和 `WITH CHECK` 都完整。严禁把 service role key 放进浏览器或提交到仓库。

### 3.4 通知

在数据库层实现，不能依赖某个浏览器一直在线：

- 当关联帖子第一次从非公开状态变为 `published` 时，给对应 Skill/Agent 的 `user_id` 发通知。
- 发帖者就是作品作者时不发自通知。
- 通知 `target_type='post'`、`target_id=<post id>`，点击后进入帖子详情。
- `event_key` 必须稳定且可去重，例如包含帖子、作品类型和作品 ID；反复审核、恢复或重试不能生成重复通知。
- 如果运营在帖子已经发布后补加作品关联，也应生成同样的去重通知。
- 现有“帖子收到回复”和“回答被采纳”通知继续正常工作，避免新增重复触发器。
- 当前没有关注系统，本轮只通知作品作者；不要为了“关注者通知”扩展新关注模块。

### 3.5 回复与返回作品

帖子详情已有回复、回复通知和采纳答案，保留并补强主链路：

- 关联作品区标题改成明确的「讨论的作品」。
- 作品卡片的操作文案为「返回 Skill 详情」或「返回 Agent 详情」，不能只显示一个没有动作含义的名称。
- 保留现有 `log_product_click` 统计；只有实际存在的合法关联才记录。
- 关联作品不可用时保留帖子内容，并显示“作品当前不可用”，不能让整个帖子报错。
- 求助帖继续支持采纳答案和“已解决”；经验帖不出现采纳操作。

### 3.6 按作品查看论坛

让 `/forum?productType=skill|agent&productId=<id>` 能显示该作品的已发布关联帖子，并在页头显示当前作品名称及「返回作品」入口。搜索、分类、排序、分页操作必须保留作品筛选参数。非法筛选参数返回普通论坛或明确错误，不能拼接进 Supabase 过滤表达式。

## 4. 交互状态与边界情况

至少处理以下情况：

- 未登录用户点击详情页发帖，登录后回到带完整关联的发帖表单。
- 作品在用户填写期间被删除或变得不可访问，提交时再次校验并给出可理解的错误。
- 发帖或关联任一环节失败，不清除草稿，也不显示成功。
- 帖子待审核时，发帖者能看到自己的帖子和关联；其他普通用户看不到。
- 帖子被驳回或下架后，不再出现在作品详情和公开筛选列表中。
- 作品作者没有账号归属 `user_id` 时，帖子仍可正常发布，只是不生成作者通知。
- 自己给自己回复、自己关联自己的作品均不产生自通知。
- 手机宽度下按钮、关联卡和帖子列表不能横向溢出；深色模式保持可读。

## 6. 验收标准

### 6.1 功能验收

1. 匿名用户分别打开一个真实 Skill 和一个真实 Agent 详情页，能看到社区讨论模块和两个发帖入口。
2. 从 Skill 详情点击「发求助」，登录后表单仍显示正确 Skill，默认类型为「求助」。
3. 从 Agent 详情点击「分享使用经验」，表单显示正确 Agent，默认类型为「经验分享」，无需填满原来的 8 个字段也能通过合法校验。
4. 提交后产生一个帖子和一个正确的 `content_product_links` 记录；重复提交不会产生重复帖子或重复关联。
5. 发帖者可查看待审核帖子；普通用户不可查看。审核发布后，帖子出现在作品详情和作品筛选论坛中。
6. 帖子发布后作品作者收到一条可点击通知；自关联不通知；重复审核不重复通知。
7. 作品作者回复后，发帖者收到现有回复通知；求助帖可采纳并显示已解决。
8. 从帖子详情点击「返回 Skill/Agent 详情」能到正确作品，并保留现有点击统计。
9. 独立普通发帖、现有后台关联、下载、搜索、论坛分类与分页没有回归。

### 6.2 权限验收

用至少两个隔离测试账号验证：

- A 能给自己的帖子建立关联，不能给 B 的帖子建立、修改或删除关联。
- 匿名用户不能写关联。
- A 不能伪造 `created_by=B`。
- 普通用户不能管理知识条目关联。
- 普通用户不能读取他人的待审核帖子或关联。
- 通知只能由接收者读取和标记已读。

如果正式环境没有可安全使用的隔离测试账号，禁止拿真实用户做写入测试。完成其余自动化、数据库权限与匿名浏览器验证，并把尚未实测的登录场景逐项写入报告，不能笼统声称端到端已通过。

### 6.3 工程验证

- 为查询参数解析、关联 payload、内容类型映射等纯逻辑补最小且有价值的测试；不要写只复述实现的测试。
- 运行 `npm run lint` 和 `npm run build`。
- 对 migration 做 SQL 审查，执行 Supabase security/performance advisors 或项目现有等价检查，处理本次新增的高风险告警。
- 在本地或预览环境进行浏览器级验证，覆盖桌面和手机宽度、浅色和深色模式。
- 检查控制台和网络请求，不能残留 4xx/5xx、重复请求或关联写入失败。

## 为什么这样改

当前产品已经具备论坛、帖子详情关联卡、回复、采纳和通知的底座，真正缺少的是普通用户从作品详情创建关联帖的能力。这个实施范围复用现有 `content_product_links`、审核和回复机制，补上双向入口、权限、作者通知和返回路径，能够以最小改动形成可演示的完整闭环。
