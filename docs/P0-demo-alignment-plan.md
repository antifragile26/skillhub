# P0｜SkillHub 演示站对齐执行计划

> 执行对象：AI 开发代理。范围仅限环境溯源、数据保护、部署对齐和演示闭环验证；不在本任务中开发审核、知识库、积分等 P1/P2 功能。
>
> 目标演示地址：`http://149.129.73.202:3015/`  
> 候选代码源：`https://github.com/antifragile26/skillhub` 的 `main` 分支  
> 候选数据源：Supabase 项目 `klkpnrkmfsvelghzplvw`（用户已提供 URL 和 publishable key；不要把密钥写入报告或提交到 Git）。

## 1. 背景与已知证据

截至 2026-09-16 的公开检查和本地检查：

| 项目 | 已观察到的状态 | 待确认的问题 |
| --- | --- | --- |
| GitHub 仓库 | 本地 `main` 的 HEAD 为 `217da8b17012547ba66b7c3a03ed3ea616aa8631`；有 `/forum/new` 和 `/forum/[id]` 页面 | 执行时重新拉取并记录最新目标 SHA；不能把这个旧 SHA 当成永久目标 |
| 仓库部署配置 | GitHub Actions 的 `deploy.yml` 在推送 `main` 时 SSH 执行 `/var/www/skillhub/deploy.sh`；该脚本 `git pull`、`npm install`、构建并重启 PM2；PM2 配置监听 3000 | Action 最近是否成功、对应哪台服务器、服务器代码 SHA、3000 是否仍为线上端口 |
| 3015 演示站 | `/` 与 `/forum` 返回 200；论坛显示“暂无帖子”；`/forum/new` 和 `/forum/1` 返回 404 | 3015 是何进程、代码仓库和提交、数据库，以及是否有其他代理层 |
| 本地运行 | 同一仓库连接候选 Supabase 项目后，`/forum` 返回 200，显示 4 个帖子链接 | 3015 是否连接另一数据库、旧版本或完全不同的服务 |

因此，**先做溯源，不根据端口号或页面品牌推定两者是同一部署**。本计划拟将上述 GitHub 仓库作为代码来源、3015 作为目标演示地址；只有在查明现有 3015 服务的用途和数据归属后，才确认切换方案。

## 2. 目标、范围与交付物

### 功能需求

- R1：能从公网地址、代理配置、监听进程一路追溯到实际代码目录、Git remote、commit SHA 和运行方式（PM2、Docker、systemd 或其他）。
- R2：确认实际使用的数据库项目、关键表结构及公开帖子数量；保留既有帖子、评论、用户及其他产品数据。
- R3：指定一个唯一的正式演示代码来源与数据来源。发布记录必须能从 GitHub 提交追溯到服务器运行版本。
- R4：线上 `/forum` 能展示预期帖子；至少一个已存在帖子的详情可打开；`/forum/new` 页面可打开。登录后的发帖与回复在隔离环境验证。
- R5：部署失败时能按文档恢复切换前的服务版本和数据连接。

### 非功能需求

- 不在公开仓库、构建日志、截图或最终报告中暴露 `.env.local`、数据库密码、SSH 私钥、`service_role` key 和完整进程环境变量。
- 不直接对生产数据库执行 seed、重建表、清空数据或整库覆盖；先比较 schema 和行数，再执行经验证的最小迁移。
- 不把未确认用途的 3015 服务替换掉。发现其为其他独立产品、其他客户数据或存在无法解释的数据差异时，保留原状并提交差异报告。
- 不把“首页返回 200”当作完成；以列表、详情、发帖页、数据一致性及部署版本证据共同验收。

### 执行完成后应交付

1. `docs/P0-deployment-audit.md`：脱敏的部署拓扑、进程/代理/代码/数据库映射、差异和决策。
2. GitHub 上可追踪的代码及部署配置改动（若需要），本地 `git status` 和对应 PR/提交 SHA。
3. `docs/P0-deploy-runbook.md`：部署、验证、回滚的实际命令与负责人可操作步骤。
4. 备份清单：备份对象、时间、存放位置、校验结果、恢复办法；报告中不包含备份内的秘密值。
5. 验收记录：每项测试的 URL、状态、帖子 ID/标题、时间、服务器 SHA 和通过/失败结果。

## 3. 执行步骤与关卡

### 阶段 A：只读盘点，建立映射

1. 在本地检查 `git status --short -b`、`git remote -v`、`git fetch origin`、`git rev-parse origin/main`、`git log -1 origin/main`。记录目标 SHA；检查 GitHub Actions 最近的部署运行结果及失败原因。不要默认 Actions 成功等于 3015 更新。
2. 从公网重测 `/`、`/forum`、`/forum/new` 和一个实际存在的帖子 URL；记录 HTTP 状态与页面可见文本。不要用猜测的 `/forum/1` 的 404 推断所有详情都坏了。
3. 通过现有的阿里云/SSH 管理入口识别 `149.129.73.202` 对应实例及其网络配置。若没有服务器访问能力，继续完成仓库侧准备，并把缺失的访问方式列为具体阻塞；不要尝试猜测凭据。
4. 在服务器上只读检查：`ss -ltnp` 中 3000/3015 的监听进程，`pm2 list`/`pm2 describe`、`docker ps`、相关 `systemctl status`、Nginx 配置与日志。根据真实 PID 查看可执行文件和工作目录。只记录环境变量**名称**与 Supabase URL 的项目标识，不输出值或密钥。
5. 对查到的每个代码目录，记录真实路径、`git remote -v`、分支、`git rev-parse HEAD`、`git status --short`、锁文件、启动命令。核实 3015 是直接监听、反向代理，还是容器映射；画出 `公网:3015 → 代理 → 进程 → 目录 → commit → 数据源` 链路。
6. 在数据库侧只读检查 `posts`、`comments`、`skills`、`agents` 的行数，`posts` 的可见样例 ID/标题，必要列、RLS 策略和迁移版本。候选 Supabase 项目也做同样检查。不要查询、导出或展示用户密码、token、完整邮箱列表。

**关卡 A：** 能明确回答“3015 跑的是哪个仓库/提交、读的是哪个数据库、为什么与本地的 4 条帖子不同”。若无法回答，不进入发布。

### 阶段 B：确定来源与切换策略

按盘点结果只选一个分支，并写进审计记录：

| 发现 | 执行路径 |
| --- | --- |
| 3015 是本仓库旧版本，数据源也应是候选 Supabase | 修复自动部署目标和端口/代理配置；先在隔离端口运行目标 SHA，再切换 3015 |
| 3015 是本仓库但使用另一个数据库 | 对比两个库的 schema、行数和业务归属；保留双方备份。确认需要保留的数据后制定逐表迁移或保留原库的方案，不直接修改 URL |
| 3015 是另一套 SkillHub 实现 | 保留原服务，在未占用的本机回环端口部署候选仓库；比较功能与数据后再确定正式演示版本，避免覆盖原服务 |
| 3015 属于其他独立服务，或数据归属不能确认 | 停止 3015 切换；提交拓扑和冲突证据，明确需要用户决定的唯一问题。仓库侧仍可完成构建与部署方案准备 |

优先使用现有 4 条帖子中的合适记录作为 P0 验收样本。若这些帖子不适合公开演示，先准备标明“演示”的样例内容供审阅；不要擅自制造看似真实的用户案例。

**关卡 B：** 有书面决定：正式演示 URL、代码源及目标 SHA、数据库源、保留哪些现有数据、采用哪种切换方式。

### 阶段 C：备份与恢复演练

1. 对识别出的原 3015 应用，记录当前 commit、进程配置、代理配置和运行参数；在服务器上建立带时间戳的独立备份，覆盖代码配置及实际使用的环境文件。校验备份能列出内容、大小合理、校验和可重新验证。备份存放在受限位置，不进入 Git。
2. 对所有可能受影响的数据库做可恢复备份。优先使用服务商现有备份机制；若具备安全的数据库连接和工具，可用自定义格式 `pg_dump`。记录备份时间、表行数、文件校验和与恢复入口。没有可验证备份时不做 schema 或数据变更。
3. 在隔离数据库或临时环境至少演练一次恢复/读取，确认备份不是空文件；如果无法完整演练，明确记录验证深度及剩余风险。
4. 写明回滚触发条件：3015 主要页面 5xx、帖子数减少、详情不可打开、数据库连接错误、登录/发帖回归失败，或运行 SHA 与发布记录不一致。

**关卡 C：** 旧服务可重启、旧代理配置可恢复、数据备份已校验且不会被新版本覆盖。

### 阶段 D：修复可追踪部署并在旁路验证

1. 在 `codex/p0-demo-alignment` 分支修改部署方案。检查当前 `deploy.yml` 只触发 `/var/www/skillhub/deploy.sh`，而 `deploy.sh` 执行不固定提交的 `git pull`、`npm install` 和 `pm2 restart`。使每次发布显式传递 GitHub commit SHA，部署该 SHA；使用锁文件对应的 `npm ci`。不要在现有运行目录上执行会丢弃未提交改动的强制重置。
2. 保留一个已构建的旧版本或独立 release 目录，发布新版本前构建并测试；记录运行 SHA（可由仅公开 SHA/构建时间的健康检查或部署元数据提供）。生产环境变量放在 Git 忽略的安全位置，检查必需变量是否存在，但不打印其值。
3. 对照实际数据库状态，按仓库迁移文件逐项检查 `posts`、`comments`、`votes` 和 RLS。只执行缺失且经验证兼容的迁移；若旧应用和新应用共用数据库，先验证向后兼容性。语义推荐所需的 OpenAI/service-role 配置不是 P0 列表/详情可用的前提，相关功能可单独降级。
4. 在未占用、仅本机可访问的端口启动候选版本。运行 `npm ci`、`npm run lint`、`npm run build`；检查首页、列表、详情、发帖页。用测试账号在隔离环境走一次发帖和回复流程，核对数据库记录。测试内容与真实内容分开，不用生产用户身份。
5. 先在旁路环境核对数据：预期帖子 ID 与标题可以读到，列表与详情一致，匿名访问符合既有产品规则，登录后操作无错误。记录候选版本 SHA 和测试结果。

**关卡 D：** 旁路版本全部通过；若有失败，修复后重测，不能因首页 200 就继续切换。

### 阶段 E：切换、监控与回滚

1. 选择低流量时段，将 3015 的代理目标或进程指向已验证的候选版本；具体使用 Nginx、PM2、Docker 还是 systemd，以阶段 A 的真实拓扑为准。保留原服务和配置，直到验收完成。
2. 从服务器本机和公网分别验证：`/`、`/forum`、`/forum/new`、选定的 `/forum/{id}`。核对运行 SHA、数据库项目标识及帖子标题。观察应用与代理日志是否有持续错误。
3. 检查切换前后 `posts`、`comments`、`skills`、`agents` 的行数；解释正常新增或变化。若出现回滚触发条件，先恢复原代理/进程目标，验证旧服务可访问，再调查原因；不要用回滚代码的方式回滚数据库迁移，除非已有单独审定的数据库恢复方案。
4. 更新运行手册：哪一个仓库/分支触发 3015、每次如何确认运行 SHA、如何查看日志、如何再次部署和回滚。GitHub Actions、服务器和演示站的版本证据应相互对应。

## 4. 验收标准（全部满足才算完成）

| 编号 | 检查 | 通过标准 | 证据 |
| --- | --- | --- | --- |
| A01 | 3015 归属 | 公网端口、代理、进程、工作目录、remote、运行 SHA 和数据库项目均有记录 | 脱敏拓扑与只读命令结果 |
| A02 | 备份 | 旧应用与受影响数据库的备份存在，校验通过，有可操作恢复步骤 | 备份清单、校验和、恢复验证记录 |
| A03 | 构建 | 目标 SHA 的 `npm ci`、lint、build 通过 | CI 或服务器构建记录 |
| A04 | 部署可追溯 | GitHub 发布记录里的 SHA = 服务器运行 SHA，3015 指向该版本 | Actions 运行记录、进程/健康检查结果 |
| A05 | 列表 | `http://149.129.73.202:3015/forum` 返回 200，出现预期帖子标题且不再仅显示“暂无帖子” | 公网页面及对应 DB ID |
| A06 | 详情 | `/forum/{实际存在的ID}` 返回 200，展示与列表一致的标题和正文；不以猜测 ID 验收 | URL、状态、可见内容 |
| A07 | 发帖页 | `/forum/new` 返回 200，表单可见；未登录用户按设计跳转登录，登录用户在隔离环境可完成发布 | 页面状态与流程记录 |
| A08 | 数据保全 | 切换前后的关键表行数和样本记录核对完成，无无法解释的缺失 | 行数对照及样本 ID |
| A09 | 回滚 | 旧版本可在明确步骤下恢复，预设触发条件已记录 | 运行手册及旁路/切换验证 |
| A10 | 秘密保护 | 提交记录与公开日志无 `.env.local`、私钥、数据库密码或 service-role key | `git status`、提交差异及脱敏检查 |

## 5. AI 执行规则与最终汇报格式

- 每阶段记录“发现、证据、决策、下一步”；实际状态与本计划的已知证据冲突时，以新证据修订方案。
- 优先只读定位，再做备份、旁路构建、切换。不要直接运行仓库的 `setup.sh`：它会更新系统、安装软件并重写 Nginx 配置，适用于全新服务器，不适用于未盘点的现有演示站。
- 不把 GitHub Actions secret 的名称当作其值已正确配置；只检查是否存在及部署结果。不要将密钥复制到聊天或报告。
- 本任务完成时报告：正式演示代码 SHA、3015 的部署拓扑、数据库项目标识、备份状态、A01–A10 的逐项结果、未完成项及准确原因。
- 若没有阿里云实例/SSH/数据库访问权限，仍完成本地与公开页面的只读盘点、仓库侧改进草案和旁路构建；最终只请求完成下一步所必需的访问方式，不推测生产环境已对齐。
